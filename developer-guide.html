1. Project & Functional Overview

BoostBuddy is a unified client management portal engineered to automate browser profiles (boxes) and social media tasks. It maps interfaces for Admins, Clients, and Employees to streamline services.

Boxes (Browser Profiles)

Admins define browser credentials manually in the database. Clients purchase these profiles as virtual "Boxes". Status tags track lifecycle stages from AVAILABLE to ACTIVE and EXPIRED.

Reviews System (Multi-URL)

Clients submit campaigns with up to 10 target Facebook URLs. The backend generates child tasks which are auto-balanced to active Employees using active workload queues.

Wallet & Credits

Credits purchased via Stripe packages are stored on client profiles and consumed during campaign orders, using optimistic locks to prevent double-spending.

Telegram Notification Bot

Dispatches localized alerts directly to users or routes notifications to configured channel groups (e.g. employee tasks queue and admin alert feeds).

4. Critical Workflows

A step-by-step trace of core execution pathways within the application.

Step 1: Client Checkout Launch

Client initiates checkout via `createCheckoutSessionAction`. For Box purchases, prices are queried securely from the database to prevent pricing manipulations. For renewals or upgrades, `calculateUpgradePriceAction` computes standard remaining day values and subtracts the proration credit.

Step 2: Stripe Transaction

Stripe handles checkout using secure checkout cards in EUR currency. A callback metadata payload links user ID, profile ID, service ID, and order details.

Step 3: Webhook Fulfillment Processing

The webhook at `/api/webhooks/stripe` catches the transaction event and forwards payload variables to `fulfillOrder`. The database saves a PAID Order record (deduplicated by Stripe session ID for idempotency). For renewals/upgrades, `ProfileAccount` resets status to ACTIVE and extends or shifts the expiration date accordingly.

Step 1: Select Wallet Package

Client chooses a package and creates a checkout session with metadata type set to `CREDITS_PURCHASE`.

Step 2: Webhook Capture

Stripe webhook captures the payment event and directs execution to the `fulfillCreditsPurchase` action.

Step 3: Optimistic Concurrency Modification

To secure user wallet modifications, `updateCreditBalanceWithRetry` runs inside `@/lib/credit-update`. It performs optimistic checks by updating database values only if current database balances match previously read ones, preventing concurrency race condition issues. If a collision occurs, it retries up to 5 times.

Step 1: Campaign Creation & Balance Check

Client fills out the multi-URL form (up to 10 URLs). `createMultiUrlReviewOrderAction` calculates credits needed against active pricing variables. It deducts the required credits using optimistic updates on `User` table, inserting a parent `ReviewOrder` and mapping the distinct target entries to `ReviewUrl` child tasks.

Step 2: Load Balancing Auto-Assignment

The server scans for available active employees (role `EMPLOYEE`, status `ACTIVE`, `acceptingOrders` `true`). It counts their active `IN_PROGRESS` tasks, selects the employee with the lowest workload, and assigns the parent order. An alert is sent to the employee on Telegram.

Step 3: Task Execution & Proof Verification

Employees claim specific URLs (`acceptUrlTaskAction`), changing the task status to `ASSIGNED`. After completing the task, the employee uploads a screenshot URL proof via `submitUrlTaskCompletionAction`. When all sibling URL tasks are completed, the parent order is marked `COMPLETED` and auto-approved.

7. Security of Sensitive Credentials

⚠️ Plain-Text Security Warning

Virtual profile credentials (browser passwords, email passwords, and 2FA secrets) are stored in **plain text** inside the database (`profile_accounts` table). Access control relies entirely on role checking inside server endpoints.

To avoid security vulnerabilities, developers must strictly adhere to the following routing rules when exposing profile structures:

  • Admin Scope: Complete access is authorized for administrators via `getProfilesAction`.
  • Client Scope: Clients fetch credentials **only** for boxes assigned to them (`assigned_client_id = user.id` and status matches `"ACTIVE"` or `"EXPIRED"`). This filter must always be enforced at the server query level.
  • Employee Scope: Employees have no access. Under no circumstances should endpoints or components query or expose `profile_accounts` fields to employees.

8. Known Issues & Technical TODOs

A list of pending inconsistencies and backlog tasks in the codebase:

1. Missing skipped_reviews Table Definition

The server file `app/actions/employee.ts` executes database selections on the `skipped_reviews` table. However, **`skipped_reviews` is not declared in `schema.prisma`**. This creates compile/runtime issues if the migration is missing from target PostgreSQL databases.

2. Unimplemented Employee Earning Actions

Database models for employee accounting (e.g. `EmployeeEarnings`, `EmployeeEarningTransaction`) are defined in the schema, but **no server actions exist to run earning adjustments or execute payments**. Accounting and payouts are currently handled manually.

3. Stubbed Cron Retry Notifications

The cron endpoint `/app/api/cron/retry-failed-notifications/route.ts` lacks functional implementation of its retry routine, containing only a `TODO` stub.

4. Telegram Component Compilation Errors

TypeScript warnings exist in `TelegramBotConfig.tsx` and `TelegramGroupManager.tsx`. Avoid modifying these components outside scheduled maintenance windows.

10. Resolved Architectural Inconsistencies

A list of codebase patterns and variables corrected to align developer expectations:

Prisma vs Native Supabase Client

Prisma is used **only** for schema architecture designs and generating SQL migrations. The application query layer uses `@supabase/supabase-js` to call PostgREST directly. Prisma Client is not imported for runtime transactions.

Realtime/WebSocket Listeners

PostgreSQL replication listens to updates on the `notification_logs` table. WebSockets refresh the SWR cache upon `INSERT` events, filtered only to `priority=eq.HIGH` elements. If the connection fails, a 30s polling fallback activates.

Development Port

The application runtime port is hardcoded in the `package.json` dev script as `-p 3400`. The server runs at `http://localhost:3400` in development.

Migration Flow

Run database alterations via `npx prisma migrate dev` in development. Apply production updates with `npx prisma migrate deploy`. Native database hooks (like replication) require manual SQL scripts.
